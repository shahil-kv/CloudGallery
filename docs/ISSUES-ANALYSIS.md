# Upstream issues: root causes and fixes

Source: every issue and pull request in [AKS-Labs/CloudGallery](https://github.com/AKS-Labs/CloudGallery/issues) as of 2026-10-23, read with comments. Root causes refer to the Android code as it was at `v0.7` (`9a55b2f`).

Status legend: **Fixed (iOS)** = handled in the iOS app. **Planned (Android)** = design below, implemented in Phase 2. Commit references are added as each fix lands.

| # | Title | Root cause in v0.7 | Fix in the new design | Status |
|---|---|---|---|---|
| 6, 34 | Video support | `LocalPhotoSource` only queries `MediaStore.Images`; the uploader and `RemotePhotoGrid` only handle images. The Bot API also caps uploads at 50 MB. | Videos are first-class items in the job queue. TDLib (user account) uploads up to 2 GB per file (4 GB with Premium); larger files are split into parts ([CLOUD_FORMAT §5](CLOUD_FORMAT.md#5-split-files)). Playback streams byte ranges. | iOS: Phase 1 · Android: Phase 2 |
| 9 | Upload stops when the screen is off | `PeriodicPhotoBackupWorker` processes at most `MAX_BATCH_SIZE = 50` items per run and relies on re-scheduling; WorkManager stops it in Doze, and failures over half the batch return `retry()` with backoff. No durable per-item state beyond `uploadStatus`. Duplicates in the comments come from items marked `UPLOADING` that never completed, then re-uploaded. | Persistent job queue (pending → uploading → verified / failed with reason) that resumes after kills and reboots. Android: long-running foreground `WorkManager` job (`setForeground`, dataSync type) with a progress notification that keeps going until the queue is empty. iOS: `BGContinuedProcessingTask` for user-started runs and `BGProcessingTask` overnight. An item counts only after Telegram confirms the message and the uploaded size matches. | iOS: Phase 1 · Android: Phase 2 |
| 10 | Encrypt before upload | No encryption existed. | Optional end-to-end encryption chosen at library creation: AES-256-GCM in 1 MiB chunks (random-access decryptable for streaming), captions encrypted too, PBKDF2-SHA256 key with 600,000 iterations ([CLOUD_FORMAT §6](CLOUD_FORMAT.md#6-end-to-end-encryption)). | iOS: v1.0 (bot) / Phase 1 (TDLib) · Android: Phase 2 |
| 13 | Tags and Aves-style features | Out of scope for a backup app. | Album names are stored in the caption so albums survive restore; full tagging is not planned. | Won't do (partial) |
| 14 | WebP uploaded as photo/sticker, re-uploaded forever | `sendDocument` without `disable_content_type_detection`, so Telegram converted small WebPs to stickers; the returned message had no `document`, so tracking failed and the item was retried. Fixed upstream in PR #28. | Every original is sent as a document with content-type detection disabled; success requires a document with matching size. | Fixed (both) |
| 17 | Cloud count wrong (200 shown, 72 present) | Counts come from the local DB (`RemotePhoto` rows), not from the channel. Rows were inserted before upload confirmation and old rows were auto-cleared (`ManageUploadsViewModel`), so the DB drifted from reality. | The channel is the source of truth: the local index is a cache rebuilt by scanning channel history. Counts are computed from verified items only. | iOS: Phase 1 · Android: Phase 2 |
| 18 | App doesn't open (Android 13, nubia) | `App.onCreate` runs `EncryptedSharedPreferences.create` and `BotApi.create()` with no error handling; a corrupted Android Keystore key (common after restore or OEM keystore bugs) throws and crashes at launch. | Startup never throws: secure storage failures fall back to resetting the corrupted keystore entry and asking the user to sign in again. Every permission and missing-config state has a screen. | Planned (Android) · iOS handled |
| 19 | "Failed to fetch update from Telegram" | The onboarding screens call `bot.startPolling()` while `scanChannelForMedia` also calls `getUpdates`. Telegram allows one `getUpdates` consumer; the second gets HTTP 409 Conflict. It also fails if a webhook is set. `getUpdates` only returns the last 24 h of updates anyway. | No Bot API and no `getUpdates`. TDLib reads full channel history with `getChatHistory`. | Planned (Android) · iOS: Phase 1 |
| 22 | "Says uploading, nothing happens" | Several silent paths: `getMimeTypeFromUri(...)!!` throws for unknown types, wrong chat IDs fail with only a log line, and the worker swallows exceptions into `FAILED` without showing a reason. | Every failure is stored per item with a human-readable reason, shown in the UI with a Retry button, and logged (secrets redacted). | iOS: Phase 1 · Android: Phase 2 |
| 23 | Upload only some photos (camera roll) | Only folder exclusion existed (v0.7). | Selection: all, chosen albums/folders, exclude screenshots, photos only / videos only, date range, Wi-Fi only, charging only. | iOS partial in v1.0 · full in Phase 1 · Android: Phase 2 |
| 24 | GPS stripped from EXIF | Not Telegram: files are sent as documents. On Android 10+ the OS **redacts location from media streams** unless the app holds `ACCESS_MEDIA_LOCATION` and opens `MediaStore.setRequireOriginal(uri)`. The app has neither. | Request `ACCESS_MEDIA_LOCATION` and always read `setRequireOriginal` URIs; upload bit-for-bit originals as documents; GPS also stored in the caption JSON. iOS: `PHAssetResourceManager` returns the untouched original. | iOS fixed · Android: Phase 2 |
| 29 | Fastlane `full_description.txt` too large (5,687 chars, limit 4,000) | Long background story in the store text. | Trimmed under 3,700 characters with a link to the README. | Phase 2 |
| 30 | Auto-remove from device after backup | Not implemented. | "Free up space": off by default, only verified items, total shown. iOS `PHAssetChangeRequest.deleteAssets`; Android `MediaStore.createDeleteRequest` or `MANAGE_MEDIA` for no-prompt deletion, plus optional auto-remove after a delay (default 7 days). Deleted items stay visible as cloud items. | iOS: v1.0 · Android: Phase 2 |
| 32 | Cloud photos stop loading after 10–12 | `RemotePhotoGrid` pages from the DB, and thumbnails were fetched with `getFile`, which fails for files over 20 MB and for stale `file_id`s; the import path also de-duplicated rows aggressively. | TDLib downloads any size; thumbnails come from the document's attached thumbnail; the grid pages over the rebuilt index. | iOS: Phase 1 · Android: Phase 2 |
| 33 | Upload stops after ~9 items | Same as #9: batch limit, Doze, and no foreground service while uploading. | Same as #9. | iOS: Phase 1 · Android: Phase 2 |
| 3 | `/start` gets no reply | Bot API onboarding depended on polling `/start` in a group, with chat-ID guesswork (`-100` prefix). | No bots: you sign in with your own account; the app creates or lets you pick the "CloudGallery Library" channel. | Fixed by design |
| 4 | Original-quality sync | Was fixed upstream by sending documents. | Originals are always bit-for-bit documents. | Fixed |
| 5 | Delete from cloud in app | Implemented upstream. | Multi-select → Delete from cloud (deletes messages, updates the index). | iOS done · Android kept |
| 7 | "Upload all" button | Implemented upstream. | "Back up now" runs the whole queue. | Fixed |
| 9 (comment) | Duplicate backups | Interrupted uploads left items `UPLOADING`/`FAILED` and the next run re-uploaded them without checking the channel. | Dedupe by platform asset ID and SHA-256 of the original, also against the channel index, so nothing is uploaded twice even after reinstall. | Both |
| 1, 11 | Reproducible builds failed (F-Droid / IzzyOnDroid) | APKs were built from a dirty tree with version bumps not committed. | Release APKs are built by GitHub Actions from the tagged commit only. | Phase 4 |
| 12 | Translations | Handled by Weblate upstream. | Kept; new strings go through resources. | Kept |
| 20 | "Abusing free services" | Discussion only; Telegram advertises unlimited cloud storage. | We stay within Telegram's limits: honour `FLOOD_WAIT`, at most 2 concurrent uploads, single account. | n/a |
| 21 | Preview before downloading | Previews were optional separate uploads. | Every document carries a ~320 px JPEG thumbnail. | Both |
| 25 | Move repo to an organization | Upstream governance. | Not applicable to this fork. | n/a |
| 27 | Bright splash in dark mode | Fixed upstream (closed). | Kept; iOS launch screen uses a dark-aware colour. | Fixed |

## Upstream pull requests

- **#26 Refactor backup architecture** (merged): SHA-256 de-duplication and an upload queue. Kept as an idea: the new queue has explicit states and failure reasons.
- **#28 DB sync, upload reliability, parallel uploads** (closed, not merged): confirms the root causes above (auto-clear of remote rows, sticker conversion, `getUpdates` only covering 24 h, 50-item batches). Its fixes are covered by the new design; parallelism is capped at 2 to respect Telegram limits.
- **#15, #16** (translations): unrelated to the redesign.
